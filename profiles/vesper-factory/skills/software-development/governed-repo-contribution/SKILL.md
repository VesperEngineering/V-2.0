# Governed-Repo Contribution

Some repos (trading systems, ML-ops pipelines, compliance-heavy codebases) carry explicit agent-governance contracts: an AGENTS.md, an autonomous-loop contract, a board/tracker file that owns "current truth", machine-readable lane/authority manifests, and receipt-based evidence chains. Contributing to these repos is a distinct class of task: the deliverable is not just working code, but code + evidence + preserved authority boundaries.

Trigger: any task in a repo containing AGENTS.md / loop.md / a "source of truth" board file, or any prompt listing hard rules like "do not run broker commands / do not promote models / do not push".

## Workflow

1. **Read governance files in the repo's prescribed order** before touching anything. Typical hierarchy (verify per-repo): board/tracker file owns current state → loop contract owns autonomous continuation rules → machine-readable manifests own lane/authority definitions → AGENTS.md is the bridge → session-handoff is resume-only and never overrides the board. Conflict rule is usually: board wins for state, **stricter boundary wins for authority**.
   - **External open-source preflight:** also read `CONTRIBUTING`, CLA requirements, AI-assistance/disclosure policy, and the PR workflow. Before choosing an issue, inspect its current assignees, recent comments, timeline cross-references, and open PRs. A `good first issue` label does not mean the work is free: exclude issues with an active PR or a contributor recently stating they are working on it. Prefer a bounded issue whose latest discussion explains the desired fix shape, then establish one known-good baseline test before editing.
2. **For huge board files (1MB+), read only the header + "Current State" section** with offset/limit. The bulk is an append-only completed-work log; the actionable fields (next task, gates, execution flags) live in the first ~100 lines. State explicitly which portion you read.
3. **Write a pre-action safety report before editing**: exact board next-task, gates that must stay closed, input files to consume, output files to create, validation commands, and whether any command writes artifacts. This is cheap and catches scope errors before they happen. Only proceed if the task is clearly inside the allowed envelope.
4. **Find the closest prior pattern before writing new code.** Governed repos are heavily convention-driven — glob for sibling task names (e.g. `*results_review*`) and clone the nearest producer's structure: same CLI arg shape, same receipt fields, same PASS/FAIL routing, same output naming. Do not invent a new shape.
5. **Read the contract tests BEFORE editing manifests/registries.** Contract tests encode hidden invariants (e.g. "lane IDs must be sorted", "every row needs field X", "broker-capable rows must require operator approval"). Reading `test_<manifest>_contract.py` first tells you where to insert and what fields are mandatory.
6. **Validate with the repo's own validators**, not just pytest: alignment validators, `py_compile`, `git diff --check`, plus the narrowest relevant test files. Missing heavy deps (pandas/torch) often break full-suite collection — run targeted files and note pre-existing failures as not-yours.
   - **Cross-platform preflight:** before an expensive first build in WSL, verify that a representative golden/test file uses LF rather than CRLF. Prefer a fresh clone made with `git -c core.autocrlf=false clone` on WSL's native filesystem. Also verify that WSL starts as a normal user rather than `root`, bridge existing GitHub CLI authentication without printing the token, and run compiler-scale first builds as tracked background jobs. See `references/windows-wsl-line-endings.md` for line-ending recovery and `references/windows-wsl-open-source-setup.md` for the full environment/bootstrap checklist.
7. **Report with the structure the governance docs demand** (files read / created / commands + status / boundaries preserved / next safe task / `git status --short`). Stop before commit/push if the session rules say so, even when the repo default says push — the stricter instruction wins; flag the deviation explicitly.

## Key techniques

- **Review-to-repair identity check**: use this only at an explicit independent-review/commit boundary or after evidence of an unexpected concurrent writer; it is not a routine agent-handoff gate. Record `git status --short`, `git diff --name-status`, `git diff --check`, the dirty patch ID, and `HEAD` before the first repair edit. A patch-ID change after an explicitly authorized repair is expected: inspect and attribute the delta, then continue when it matches the approved scope. Stop only for unapproved or unexplainable movement. Keep the repair unstaged unless explicitly authorized; after final verification, record the current patch ID and status once for the next real decision point. For pytest, create the requested external same-drive `--basetemp` parent before launching the suite so a setup-only path error is not misclassified as a source regression. For a staged-candidate integration sequence, see `references/frozen-candidate-repair.md`.

- **Broker protective-order architecture review**: treat the broker as the source of truth and require explicit invariants before approving unattended execution: exact protective coverage of broker-confirmed filled quantity, no competing exit writers, fill-driven state transitions, deterministic client-order IDs, single-writer leases, and startup/periodic reconciliation. Reject global open-order cancellation, mutable JSON as execution authority, module-global daily counters in per-run subprocesses, and any design that marks positions closed on order acceptance rather than confirmed fills. Verify order type/TIF support for whole versus fractional quantities, use exchange calendars rather than weekday/fixed-offset checks, and backtest stop-market gaps at open-or-worse rather than assuming fills at the trigger. Use `references/broker-protective-order-safety.md` for the full failure-mode and deployment-gate checklist.
- **Read-only broker/execution safety audit**: trace every side-effect boundary, not just the guarded top-level CLI. Identify whether transport failures are `no order`, `order accepted`, or `unknown`; a timeout/connection reset after POST must never be converted into a retryable `NO_ORDER` result. Require exact endpoint allowlisting (parsed scheme/host, not substring matching), exchange-calendar session validation, and reconciliation keyed to a deterministic client order ID rather than “latest order for symbol.” Inspect tests for ambiguous POST outcomes, holiday/early-close dates, pending/canceled/multiple same-symbol orders, and direct invocation of lower-level submit functions. Run focused tests plus one no-network guard probe, and report infrastructure/test-harness failures separately from behavioral results. See `references/read-only-execution-safety-audit.md` for the audit matrix and reproduction recipes.
- **Autonomous steward command authority**: never execute tracked lane strings with `shell=True`, and never treat a denylist of symbolic action names as a security boundary—equivalent commands, script wrappers, and compound shell expressions bypass it. Keep the steward signal-only where possible. If it must run recovery, map a small symbolic action ID to a hardcoded argv list, call `subprocess.run(argv, shell=False, ...)`, and reject every unrecognized action. Persist work-packet claims before delegation for exactly-once behavior, make completed/disabled/claimed lanes ineligible, and keep unchanged recovery skips cycle-neutral and silent.
- **Receipt-parity refactoring**: when refactoring an output-producing module (report generators, receipt writers), regenerate the output through the new code and assert field-by-field equality with the pre-refactor output (excluding timestamps). This proves the refactor is behavior-preserving in a way unit tests alone don't. Keep the module's public API (function names + kwargs) identical so callers/CLI never change.
- **Config-over-clones**: when a repo has dozens of near-identical scripts (~90% shared skeleton), build a shared framework module + per-task config dataclass, migrate ONE module as proof with parity check, and leave the rest untouched. "Smallest change" rules in governed repos forbid mass rewrites; additive framework + single migration is the acceptable shape. Framework should use `@dataclass(frozen=True)` for the config, with `Callable` fields for task-specific evidence checks. Make boundary keys, authority output keys, what_this_proves lists, mode labels, and summary labels configurable (different task families use different key sets and field names). Field ordering in the dataclass IS critical: in Python, `@dataclass(frozen=True)` enforces that all fields with defaults must come AFTER all fields without defaults — Python raises `TypeError: non-default argument follows default argument` at class-definition time if you place a default-having field before a no-default field. Put all diverse default-having fields (differing across task families) last in the class definition, and keep the required-shared fields (task_id_template, ready_decision, etc.) first. This is not optional — the class won't compile otherwise.
- **True --dry-run**: repos may use "dry run" to mean "no dangerous action" while still writing files. When adding a real preview mode, make it validate + print would-be paths + exit with zero filesystem writes, and add a test asserting the output dir stayed empty.
- **Fail-closed producers**: evidence/receipt generators should append a failure string per violated invariant, dedupe+sort, and derive PASS/FAIL from emptiness of the failure list. Never weaken a validator to make a receipt pass.
- **Trace receipt consumers backward to producers**: when a gate reports a missing receipt, do not stop at the validator or manually create a placeholder. Enumerate the exact accepted filenames, required status envelope, fields, and upstream artifacts; then add an explicit producer stage to the authoritative pipeline at the point where those artifacts become available. Verify the producer with the real scheduled interpreter and rerun the consumer end-to-end. Keep three states separate: receipt exists, receipt is evidence-valid (`STATUS: PASS`), and execution/pretrade is authorized. A valid candidate report may still contain `Operator decision: hold for review`; never promote that field or a receipt envelope into order authority.
- **Current-source receipt selection**: a current operational flow must never fall back from its configured source to any status-only legacy or alternate-source receipt. Bind the consumer to one dated authoritative producer plus its structural validator; validate source identity and actual freshness/date values, not merely the presence of labels or a top-level `PASS`. Missing, malformed, stale, mismatched, or validation-only receipts must fail closed. Add adversarial regressions for a `STATUS: PASS`-only sibling, legacy alternate-source-only evidence, and contradictory expected/local dates.
- **Missing candidate inputs are an authority gate, not a report-formatting defect**: trace a non-green candidate report backward only far enough to inventory its producers. A read-only candidate renderer may truthfully emit a dated fail-closed/no-action receipt; it cannot justify inventing scores, reusing stale baskets, or running the upstream factor pipeline. Before producing dated factor scores or a basket, enumerate every source/provider capability, database/history write, output path, and whether the step creates a fresh ranked/basket strategy decision. Treat a provider-capable factor runner, factor-history append, or basket-selection write as a separate exact-scope authorization boundary even if the desired downstream preview is `--no-submit`. The authorization must name the date, allowed providers and writes, whether a new strategy decision is permitted, and explicit denials for source switching, model training/promotion, broker/account/order, scheduler/risk, and secrets; any separately governed provider retains its own attestation requirement. If that authority is absent, preserve the non-green candidate receipt, record the exact missing inputs, and stop before pretrade.
- **Repairing a receipt reader requires regenerating its dated producer receipt**: changing a parser/consumer does not alter an existing generated Markdown receipt. After a reviewed reader or tracker-pointer repair, run the authoritative *local/no-network* producer for the same date, run its structural validator, and print the exact date/status fields the consumer uses before the single end-to-end no-submit probe. Interpret the probe in stages: `active evidence PASS + candidate missing` closes the data-routing defect and opens a separate candidate-evidence task; do not weaken the active reader merely because the next gate is still closed. Update the durable tracker/visual to name the first remaining gate, not the superseded one.
- **Prove the unattended path, not only the manual path**: after adding pipeline stages, inspect every producer's CLI contract against the scheduler's actual invocation. A script that requires `--date`/other arguments while the pipeline launches it with no arguments is a latent scheduled failure; either pass explicit arguments through the step model or provide a safe date-default contract and test both paths. Run the full ordered pipeline with the exact scheduled interpreter, capture every stage's start/completion and exit code, then trigger the actual OS task and verify `Last Run`, `Last Result`, `Next Run`, exact action path, and generated receipts. A dry-run and a manually generated receipt are insufficient. Treat `Status: Ready` as configuration only, and distinguish a historical task failure from the fresh end-to-end result.
Do not let a stale/alternate model report pass merely because it has plausible candidates. Preserve separate fields for candidate evidence validity, operator decision, and execution intent.
- **Staged bounded-paper execution**: keep the authoritative factor pipeline, no-submit preview, governed operator-intent loop, and post-order reconciliation as separate stages. A green candidate/no-order receipt is evidence, not order authority: `Execution mode: no_order` or `Operator decision: no action` must never reach pretrade or any broker GET/POST. Do not wire a generic OS scheduler directly to a submitter. Scheduled surfaces remain preview/reconciliation-only unless the project separately grants exact scheduler authority and supplies an authenticated, exact `paper_order` intent for symbol, side, and notional; otherwise non-preview submission must flow through the governed daily loop. The submit lane must select from the same admitted factor-basket receipt the preview consumed, while the low-level guard must preserve the currently approved board envelope (including an explicitly approved symbol such as AAPL) until a dated authority artifact widens it—candidate membership alone does not widen authority. Require exact symbol/side/notional parity between candidate intent and pretrade readiness, enforce paper endpoint + side + notional bounds in the low-level submitter, and reconcile the deterministic client order ID before POST. A new POST requires provider-proven absence—typically the exact `by_client_order_id` endpoint returning `404`. Treat `401`, `429`, `5xx`, invalid JSON, identity mismatch, timeout, and any other non-404 preflight response as `ORDER_STATUS_UNKNOWN` with POST/retry blocked. **After a POST has been attempted, a follow-up `404` is not proof that no order exists**—it may be eventual-consistency lag after an accepted request. Only an exact deterministic-ID reconciliation may convert that state to `PASS_ORDER_RECONCILED`; every other post-POST result must latch `ORDER_STATUS_UNKNOWN` and block retries. Record submission truth as tri-state when needed (`true`, `false`, `unknown`): never report `false` merely because a successful/attempted POST returned malformed or identity-mismatched content. Put accepted lifecycle statuses in one shared predicate (submitted, exactly reconciled, and same-envelope-already-exists where applicable) and use it across the daily loop, reconciliation monitor, fill evidence, portfolio evidence, and validators. Fill generation must query and verify the exact deterministic client-order ID plus date/symbol/side/notional; never select the latest same-symbol order, and do not perform position reads until exact order identity is proven. If a same-envelope local receipt is already accepted, return it idempotently rather than performing another GET/POST; a different envelope triggers the daily latch. Verify any approved real OS task's action path/schedule/Last Result/Next Run, and run the exact scheduled interpreter end-to-end before claiming the lane works. Update tests for no-action non-routing, fixture provenance, exact scope fields, provider-proven-absence preflight, ambiguous-response blocking, holidays/early closes, reconciled-status consumers, and unrelated same-symbol orders; never weaken production guards to preserve legacy fixtures.

- **Factor portfolio backtest**: combine weak cross-sectional features into a daily rank-based portfolio. Top quintile each day by combined signal, measure forward return vs equal-weight. Use non-overlapping periods (step by horizon days) — compounding overlapping forward returns produces absurd numbers. The output is a clean Sharpe/total-return/drawdown/hit-rate comparison. Weak features with CS-ICs of 0.02-0.05 can compound to a real edge: +40% relative outperformance over 49 non-overlapping 10d periods in Vesper's 30-ticker basket.
- **News sentiment feature**: load headlines from the project's news archives (WebZ JSON, FinViz scraper), score via dictionary sentiment (no deps), compute cross-sectional IC vs forward returns. Dictionary sentiment at 21d produced IC of 0.049 for Vesper — comparable to top technical features with a single date of data. For production: backfill 30+ days of headlines, add rolling average sentiment as a daily feature in the factor IC pipeline. See `references/vesper-quant-patterns.md`. in Vesper and similar ML/trading repos. Load OHLCV, compute features via the project's own `calculate_features()`, compute forward returns at multiple horizons (5/10/21d), and calculate Spearman rank IC per feature-horizon pair. Skip NaN ICs from constant features (macro overlays, calendar encodings). The output is a decay-curve table showing which features actually predict returns — replacing hardcoded `rank_ic_floor: 0.02` governance placeholders with measured values. When loading from sharded coverage DBs, batch per DB (one `WHERE ticker IN (...)` query + `df.groupby("ticker")`) — this is ~37x faster than per-ticker queries. **CRITICAL PITFALL — pooled IC != cross-sectional IC.** Pooled ICs (concatenating all ticker data before correlating) inflate ICs by 20-40x from autocorrelation (vwap_dist 0.84 pooled -> 0.02 cross-sectional). Always compute per-date cross-sectional ICs via `panel.groupby(panel.index)` then Spearman per date; cross-sectional ICs of 0.02-0.05 are competitive for equity factors — don't discard them as noise. See `references/vesper-quant-patterns.md` for the full pipeline, data-loading pitfalls, cross-sectional IC computation, and factor portfolio backtest techniques.
- **Doc-drift repair**: when two governance files disagree on a current-state value (e.g. one says `Execution allowed: false`, the board says `true`), the fix is to make the stale file DEFER to the board ("preserve the board's flags exactly as stated; never widen them") rather than hardcode the new value — hardcoding just recreates the drift later. Check for tests asserting on doc content before editing docs.
- **Current-state fact-base reconciliation in an isolated worktree:** first run the repository freshness validator to enumerate stale fact-base dependencies (board fields, manifest lane map, open-issue map, and current-document markers). Parse current canonical board labels with legacy fallback only when the canonical value is absent; do not let a parser miss silently become an unknown operating fact. If a board summary conflicts with dated evidence, reconcile only from a named, structurally validated receipt that directly states the field; otherwise preserve/mark it unknown. Update the board summary before its fact base, then only the user-facing docs that repeat verified facts. Add a regression proving the checked-in fact base validates against the checked-in board, manifest, issue registry, and required docs. Run the validator from the candidate worktree so it validates candidate source and document paths, not an adjacent canonical checkout.
- **Governance-state integration after merges/cherry-picks**: do not resolve a conflicted authority document by wholesale `ours`/`theirs` selection. That can silently roll back a newer, evidence-backed current-state update while preserving the surrounding document. Before resolving, inspect the successor commits that touched the authority file and preserve the newest receipt-backed header/current-state fields. After integration, run the repository’s tracker-consistency validator and focused drift/sync tests before committing; repair the authoritative board from the verified commit/receipt, then let dependent handoff and memory surfaces defer to it.
- **Fresh-worktree direct integration and push**: after `git fetch origin <branch>`, prove the candidate parent equals the refreshed remote tip and compare the candidate’s changed-file list with the remote-advance file list before creating a new integration worktree. Cherry-pick into a branch based on that exact remote tip; do not use a dirty source checkout or update canonical merely to integrate. A fresh worktree commonly lacks ignored local tooling such as `.venv`; run verification with the project venv’s absolute interpreter while setting `PYTHONPATH` to the integration worktree, so imports and test collection exercise the integrated source rather than an adjacent checkout. Create external same-drive basetemp roots. Before push, fetch again and require `origin/<branch> == HEAD^`, a clean worktree, and `git diff --check`; after `git push origin HEAD:<branch>`, fetch and require `origin/<branch> == HEAD`. If an independent review has outstanding findings but the human explicitly directs the push, report that the push follows explicit direction and retain the findings as an open follow-up rather than representing the candidate as unconditionally approved.
- **Frozen narrow-candidate integration into a dirty canonical checkout**: when an independently reviewed patch must land from an isolated worktree while canonical has unrelated local dirt, freeze and bind the source *before* the first write: record source branch/HEAD, require `git diff --cached --name-only` to equal the approved allowlist, require `git diff --cached --check`, bind `git diff --cached --binary | sha256sum`, and require no tracked unstaged source diff. In canonical, record `git status --short`, branch, and HEAD; verify both index and worktree are clean for every target path (`git diff --quiet -- <paths>` and `git diff --cached --quiet -- <paths>`). Do not use `stash`, `reset`, `checkout`, or broad add commands to clear canonical dirt. Commit the exact allowlisted source paths, then cherry-pick that commit into canonical; this preserves unrelated canonical modifications. Immediately prove the canonical commit’s changed-file list is exactly the approved scope and contains no governed-neighbor paths (e.g. observer/ledger artifacts). Run the required focused test, lint/compile, diff checks, and temporary GUI smoke from canonical, then push only after those gates pass. Report both the source and canonical commit SHA: cherry-pick may create a distinct canonical SHA even when content is identical.
- **Broad dirty-canonical recovery via a safety ref**: when canonical has many legitimate tracked/untracked changes and the candidate spans multiple reconciled slices, do not rely on stash/reset or the narrow allowlist recipe alone. Build from the exact remote base in a clean integration worktree; preserve canonical tracked dirt on a separate `preserve/...` branch by applying `git diff --binary` into another worktree and committing it; verify every working blob/deletion against that safety commit; separately intersect candidate-added paths with canonical untracked paths, back up each collision byte-for-byte outside the repo, and verify SHA-256 equality. Freeze and review the full containing SHA—not an earlier coordinator commit—and keep focused gates, broad-suite failures, and machine-local artifact coupling distinct. In dependency-based Kanban, a review card parented to a still-running goal may never dispatch; complete the dependency first or keep the review standalone and bind it in comments/receipts. See `references/dirty-canonical-recovery.md` for the complete preservation, collision, validation, review, and integration sequence.
- **Canonical branch synchronization and hygiene:** when the user asks to make a canonical repository "current and clean," make "current" and "clean" separately provable. First fetch the declared upstream and record `HEAD`, `origin/<branch>`, and `git rev-list --left-right --count HEAD...origin/<branch>`; inspect `origin/<branch>..HEAD` before publishing local-only commits. Classify tracked dirt, untracked source/docs, generated test scratch, runtime/audit state, and linked worktrees before writing. Preserve unreviewed/untracked source notes and sketches outside the checkout rather than deleting or blindly committing them; remove a scratch root only after proving it contains no tracked files. Never use broad `git clean -fdX` in a governed checkout: ignored paths may include active linked worktrees or other valuable local state. Add only narrow, repo-appropriate ignore rules for generated scratch, then stage and inspect the exact cleanup diff. Push and verify both `git ls-remote origin refs/heads/<branch>` and a post-push fetch show `HEAD == origin/<branch>` with `0/0` divergence and empty porcelain status. If the remote reports a protected-branch bypass, state that exactly—remote SHA equality is not proof the normal branch-protection workflow was followed. Run the narrowest relevant policy/commit-guardrail test under the project interpreter with an external same-drive pytest temp root. If that test regenerates an untracked artifact, compare it byte-for-byte with the preserved copy before removing it; otherwise preserve the new bytes. Finish with `git fsck`, final status, and SHA equality. This produces a 1:1 canonical branch without silently losing local work.

- **Strictly read-only exact-merge authorization audit**: when the user supplies an exact base, candidate, isolated merge, frozen dirty-checkout manifests, and existing gate logs, audit without creating refs, worktrees, pytest scratch, caches, or receipts unless the prompt explicitly permits external scratch. Use `GIT_OPTIONAL_LOCKS=0`; prove ordered merge parents, candidate/merge tree identity, and either exact-base descendant ancestry or an **explicitly bound tree-neutral sibling topology** where the canonical base changed ancestry but not content relative to the candidate parent; recompute binary-diff and exact path scope; check exact, case-folded, exact-prefix, case-folded-prefix, ignored, reparse-parent, and filesystem collisions; verify every dirty manifest file/symlink byte-for-byte; authenticate focused/broad logs by hash; compare broad failure node IDs as exact sets and order rather than counts; and recheck concurrent drift immediately before `PASS`. Predeclare which refs/worktrees are authoritative bindings so movement of an ancillary inferred branch to a clean descendant is not misclassified as a material blocker while exact SHAs and evidence-named worktrees remain pinned. If fresh tests are required and external scratch is authorized, use a detached external Git clone at exact merge `M`—not an archive-only tree when tests may invoke `git rev-parse`—and route basetemp, bytecode, and generated artifacts there. See `references/read-only-isolated-merge-audit.md` for the full fail-closed recipe, both safe topology classes, ignored-path exit-code handling, broad-summary parser variants, and bounded verdict language. If the user requires the final response to be **exactly** `PASS` or `HOLD`, emit one token only—keep the detailed machine-readable report and fresh-gate logs in authorized external scratch rather than appending an explanatory summary.
- **Kanban review-gate lifecycle**: a completed implementation and its independent review are separate states. Before dispatching a child review that depends on an implementation task, record the implementation’s required completion metadata and mark that implementation task `done`; a `blocked` parent prevents the dependency engine from claiming its review child. For receipt-bound exactly-once review, keep the reviewer behind a durable dependency/hold while attaching the pending receipt and materializing its exact-source worktree—an initial `blocked` label without a persisted blocker may be auto-promoted. Re-read live run history and require zero runs before lifting the hold, then dispatch at most one reviewer. If setup failure creates any run row, archive that card as inadmissible/no-verdict and create a fresh reviewer ID; never retry or repurpose it. Never force-promote the review merely to bypass an unfinished parent. A rejected review must create or requeue an explicit revision task with the reviewer’s exact findings, keep deployment/canary authority closed, and require a fresh independent review after the revision. See `references/lifecycle-ledger-independent-review.md`.
- **Triage is not inherently a durable human hold**: inspect the exact installed CLI, gateway sweeps, and effective runtime configuration before treating a status name as an authority boundary. A gateway may automatically send triage cards to an auxiliary provider, decompose/specify them, promote children to ready, and dispatch workers after its next tick. A short post-create observation shorter than the configured tick interval is not evidence of durability. Exercise the exact sweep against an isolated board, trap provider calls, inspect child tasks/runs/events, and make idempotent replay reject or truthfully report cards that have left the expected hold state. Also trace shared snapshot/load functions transitively: a superficially disabled telemetry argument may still call provider-accounting APIs or write caches. See `references/kanban-triage-and-transitive-side-effects.md` for the full audit checklist.
- **Kanban budget and frozen-candidate preflight**: do not treat a positive card-level `--goal-max-turns` as sufficient proof that a worker can act. Before dispatching a goal-mode Planner, Builder, or Reviewer, verify the assignee profile has a strictly positive `agent.max_turns` too; a profile value of `0` can yield immediate `Iteration budget exhausted (0/0)` before the goal loop reaches its declared card budget. Use bounded positive profile budgets and retain a positive per-card goal budget as separate evidence. At review start, freeze the candidate: record base SHA, candidate SHA, canonical diff digest, and clean worktree status; ensure no Builder card remains runnable in that workspace. Archive or triage superseded review/retry cards so stale workers cannot enter the frozen worktree. After every archive, parent-status change, or dispatcher recovery, explicitly verify `hermes kanban --board <board> list --assignee <role> --status running` and `dispatch --dry-run`: stale cards can be re-promoted or retain per-profile capacity after parent reopening. Do not dispatch a reviewer until the only runnable card in that workspace is the frozen candidate review; never let an old Builder task resume in the review worktree.
- **No-helper atomic authorization audit**: when a Python candidate claims that outcome computation is reachable only through one atomic authorization entrypoint, inspect both the frozen staged blob and the imported module. Inventory every module-local callable, signature, closure, nested code object, block field, and outcome-arithmetic site; reject any exposed row/block-to-outcome helper, reusable authority capability, or phase-integrity helper that returns protected rows. Probe cross-database substitution, requested-partition isolation, contract/database TOCTOU, and final-phase ordering with loader/builder sentinels. A valid self-sealed final manifest may pass integrity-only CLI validation but must still reject outcome evaluation before rows load. Keep the boundary explicit: Python is not a hostile in-process sandbox, and manual arithmetic reimplementation is not an exposed helper. On Windows, run SQLite probes as child processes and clean fixtures from the parent after exit. See `references/no-helper-atomic-authorization-audit.md`.
- **Adversarial fail-closed evidence review**: operator state, completion, approval, objective, and action-receipt models need runtime-adversarial review beyond typed happy paths. Probe exact booleans, malformed/subclassed IDs and timestamps, hostile `__eq__`/`__hash__`/conversion/timezone behavior, duplicate identities, whole-model hashability, and state-dependent source completeness. A `FRESH` enum without nonempty parseable observation and provenance is not freshness proof. Review the exact frozen `base..candidate` range; failed candidates remain auditable and repairs use successor commits. After two failed review/fix cycles, stop autonomous churn and present cumulative findings plus one recommendation. See `references/fail-closed-evidence-model-review.md`.
- **Stage pacing and reviewer-audit discipline:** before advancing any governed stage, read the session todo list and the exact board-card state; finish or explicitly block the current stage before opening the next. Work in small Kanban increments: builder → freeze → independent review → integration → real end-to-end probe. When the user directs autonomous continuation, do not pause for routine preflight ambiguity, receipt-correction decisions, TDD repair sequencing, or format-bridging choices — those are engineering decisions, not authority gates. Independently run bounded preflights, receipt corrections, focused validation, review, and tracker/visual synchronization. Only present options to the user at a genuine new authority boundary: provider call, dependency install, fresh factor/basket decision, source switch, or broker/order action. When presenting, give one clear recommendation with scope, not a menu — the user corrects scope, they don't architect the approach.

If an independent reviewer rejects the architecture because it validates self-reported evidence instead of producing authoritative evidence, do not stack more syntactic checks onto the same candidate: preserve the rejection receipt, freeze the worktree, and re-plan a trusted producer/coordinator in a fresh worktree. If the reviewer provider blocks the review before executing it, record that as a **no-verdict capability failure**, not PASS or FAIL. Preserve the frozen candidate and blocked-card log, then use an approved alternate reviewer provider or a human review path; do not retry the same blocked prompt indefinitely or convert an operator acknowledgement into technical approval.
- **Shadow handoff and review-receipt discipline:** when bridging a coordinator to a durable board, build a read-only packet from coordinator status rather than from board labels. Bind workflow/task ID, candidate/tree/diff, evidence root, state, next role, and explicit false authority flags. A completed reviewer card is not sufficient evidence by itself: compare its retained log to the exact required commands and candidate. Missing command-level output, API stream failure, a partial suite, a checkout-local test artifact despite an external-temp requirement, or SHA/diff drift is a **no-verdict**. Preserve that receipt, clean only the known scratch artifact, keep the candidate frozen, and obtain a fresh independent review. Before a live shadow exercise, run the exact installed CLI/backend against an isolated temporary board and make mocks use the observed JSON schema—not an assumed one. Validate result field types and persistence limits too; for SQLite-backed handoffs, an integer timestamp must be a positive signed-64-bit value. If the backend commits a valid atomic handoff but the adapter rejects its response, immediately reclaim/archive the destination before review, preserve the receipt as failure evidence, and never reuse that source task or transition key; repair in a fresh candidate, re-review, and exercise with a fresh workflow/source binding. See `references/trusted-delivery-shadow-handoff.md`.
- **Reconcile all state readers, not just the visible board:** before archiving stale cards or declaring a board cleanup complete, identify the concrete readers used by freshness/preflight and operator surfaces. A legacy local-pointer reader may not consume Hermes Kanban state. After reconciliation, execute the exact no-network preflight; an `unknown` task pointer is a fail-closed integration defect, not a reason to force a green result or proceed to refresh. Track that defect as a blocked repair and keep refresh/order authority closed.
- **Tracker-pointer parser safety:** current-state Markdown is an interface, not free-form prose. When labels evolve (for example, from `Last completed task` to `Last completed operating task`), make readers prefer canonical labels with legacy fallback. Parse the first fenced task before a governance suffix such as `; last completed governance task: ...`; accept deliberate plain-text next-action pointers only when non-empty; otherwise return `unknown`. Add a hermetic regression fixture matching the exact canonical tracker shape, retain a legacy fixture, and run the real no-network consumer after the focused test. Never make an `unknown` pointer disappear by weakening a downstream validator or inventing a task value.
- **Kanban isolation before readiness:** a `dir:<path>` card can resolve to the dirty canonical worktree. Before any code card can become ready, create or verify a clean isolated worktree at the exact base SHA and make the card resolve there. Do not chain worktree preparation and `kanban create` with a shell separator that continues after failure; use a dependency-stopping command chain and explicitly inspect the worktree status before creating the card. Inspect the card immediately after creation: gateway dispatch can claim or promote it sooner than expected. If setup fails after a card is created, archive that card immediately and create a fresh isolated replacement rather than repairing its workspace in place. When a Builder reaches a review boundary, reclaim and block it before review so it cannot resume edits; freeze the candidate, then queue the reviewer against that exact worktree/SHA. If an initial card was misconfigured to use canonical state, archive it and create a fresh isolated replacement rather than overriding the safety boundary.
- **Ignored operational data versus code isolation:** clean worktrees commonly omit ignored databases, caches, and generated receipts. A missing path in a worktree is not proof that the canonical input is absent. Check canonical existence plus size/mtime before classifying the blocker. If a task is strictly read-only, fixed-argv, and writes only a named ignored receipt, it may consume canonical operational inputs while code changes remain isolated; record pre/post metadata for protected inputs and active-state sentinels. Provider calls or staged-output writes still need exact authority and a canonical-context preflight. Never use this exception to edit a dirty canonical checkout. See `references/vesper-ignored-data-worktrees.md`. For byte-identical admission of a protected ignored artifact, strict loader/schema gates, tracked receipt binding, review-freeze ordering, and dirty-canonical integration, see `references/protected-data-admission.md`.
- **Producer-universe alignment is an authority check.** Never infer a factor/basket producer's universe from a downstream active-data envelope. Read its actual configured universe, source registry, date/cutoff, and writes before dispatch. If a requested 30-symbol envelope and a canonical 502-symbol producer differ, stop before the first provider call; record the mismatch and require an explicit human scope amendment or a purpose-built bounded producer. Preserve every other denial when only the universe changes.
- **Failure receipts must be internally truthful.** Independently compare timeout fields with process `timed_out`, elapsed time, exit code, and captured failure tail. A pre-import/runtime failure must not be labeled as a timeout or provider failure. Treat contradictory failure metadata as an evidence-integrity defect: preserve the no-execution outcome, repair semantics in an isolated TDD task, and obtain fresh review before using the receipt to route remediation or authorize a retry. An authorization for one invocation does not authorize a retry after a code or environment repair; bind the later execution to fresh explicit scope.
- **User-facing governed-repo reporting:** for this user, present complete state, results, issues, and retained authority boundaries together first; finish with one clear recommendation. During long-running tests, builds, delegated reviews, or integration gates, send a brief progress update about every 30 seconds when the platform permits, naming the current step, latest verified result, blocker, and remaining work; do not leave extended silent waits. Do not scatter findings across multiple partial updates or inflate an approved-not-shipped attestation into execution authority. When the user asks to **open**, **pull up**, or **show the review document**, launch the exact complete reviewer-report artifact in their desktop application and report its path and verdict. Do not substitute the master engineering document, a summary, or an approval-choice prompt.
- **Evidence-pipeline bridging**: when a downstream consumer expects a different evidence format than the available upstream artifacts (e.g. the daily loop expects `daily_no_order_report_*` but the factor+basket producer outputs `factor_scores_*` + `sector_basket_*`), build a minimal bridge script that converts the available artifacts into the consumer's expected format rather than modifying either producer or consumer. Validate that the bridge output satisfies the consumer's receipt-status parser (`STATUS:` field, `_receipt_is_green()`, etc.). Keep the bridge shallow: a single file, no new dependencies, no provider calls, no database writes. Test end-to-end by running the consumer against the bridge output. The bridge is a wiring adapter, not a new producer — do not reuse it to fabricate evidence whose upstream artifacts do not exist.
- **Receipt authenticity and bounded validation**: an immutable validation receipt must bind a canonical digest of the exact validated payload, alongside identity/schema/status fields. Otherwise a changed payload can appear covered by an old PASS receipt. For recurring validators, bound input bytes, string/list cardinality, evidence-reference count, per-file hash size, and aggregate hash work; fail closed on every exceeded budget. JSON byte limits alone are insufficient: after bounded reads, treat parser recursion/depth failures as malformed input, validate exact scalar types before set membership or comparisons (especially reject `bool` where an integer is required), and ensure malformed prior status cannot suppress recovery from a valid authoritative receipt. Security regressions for symlink/path escape should capability-probe the host rather than blanket-skip by OS when the host can create symlinks.
  - **Bind receipt paths separately from receipt bytes.** A SHA-256 match proves content identity, not exact lineage: a same-byte alias can satisfy a hash-only check. When a receipt must supersede one exact predecessor, first require its declared repository-relative path to equal the expected path, then read and hash the bytes at that validated declared path. Prove the repair in a disposable frozen-candidate snapshot by substituting a same-byte alias and requiring failure at the path assertion. Ensure pytest actually runs with the snapshot as its current working directory; otherwise the probe can falsely pass against the source worktree. See `references/receipt-path-binding-review.md` for the full review and harness recipe.
  - **Hash the frozen Git representation, not incidental checkout bytes.** During final staged review, recompute every receipt-declared source hash from the index (`git show :path | sha256sum`) and compare it with the receipt. On Windows, `core.autocrlf=true` can make raw working-tree SHA-256 values differ from canonical staged blobs while `git diff` remains clean. A newly created LF file may match the index while older CRLF files match only the worktree, producing a mixed, checkout-unstable receipt. Treat that as a blocking receipt-integrity error even when behavior and tests pass. Prefer canonical staged-blob hashes and bind the staged tree ID or complete staged binary-diff digest. If an already-immutable receipt is wrong, preserve it and issue a superseding correction receipt rather than silently rewriting history. For the cross-platform regression and non-circular binding recipe, see `references/windows-git-receipt-code-identity.md`.
- **Concurrent JSONL evidence ledgers**: direct `open(..., "ab")` after an unlocked replay is unsafe: two resident writers can derive the same head, lose an update, or fork a hash chain; a partial live-file write can corrupt the ledger. A SHA-256 binding alone is also insufficient: parse the allowlisted completed receipt and **derive** every asserted field (identity, observation time, state/freshness, reason, provenance, and binding) from it; reject any caller event that is not exactly equal to that derivation. This blocks arbitrary bytes with a matching hash and caller-relabelled `FRESH` evidence. Acquire a bounded interprocess writer lock, then *inside the lock* re-check receipt semantics and reload/revalidate the full chain head before duplicate/order decisions. Construct `prior_valid_bytes + one canonical newline-terminated entry` in a unique same-directory temporary file, flush + `fsync`, then `os.replace` atomically; clean up only that owned temporary file on failure. Reject any nonempty ledger without a terminal newline as interrupted, and never append to a malformed/tampered chain. Serialize the separately published status summary too, and retain a structurally valid existing summary whose evidence timestamp is newer-or-equal so a delayed observer cannot regress the read-only view. Use `multiprocessing.Barrier` rather than sleep-only timing in spawned-process tests to force lock contention. Cover duplicate/current-evidence races, status-publication races, receipt-semantic forgery, caller relabelling, hash tampering, truncated-final-record, and forced-replace-failure preservation. On Windows, use an external same-drive pytest basetemp.
- **Lifecycle-ledger independent review and candidate rebinding**: validate every receipt history before any matching replay/no-op return; compare non-state identity through canonical JSON bytes rather than Python equality (`False == 0` and `1 == 1.0`), allow only exact monotonic state sequences, and make unrelated appends fail over corruption anywhere in the ledger. Exercise valid transition, exact replay, mutated history, unrelated append, reverse order, duplicates, CLOSED-first, scalar-type mutation, and concurrent thread/process append. On Windows, layer a canonical-path process-local thread lock before `msvcrt.locking` and stress multiple rounds because one barrier run can miss `Errno 36` contention. If another actor commits an uncommitted candidate during review, rebind only when the exact baseline-to-HEAD binary patch digest equals the last reviewed working-diff digest and the file allowlist is unchanged; rerun post-commit gates and report the empty current diff separately. See `references/lifecycle-ledger-independent-review.md`.
- **Immutable correction receipts for contradictory evidence metadata**: when a freeze-reviewed fail-closed execution receipt contains a contradictory metadata field (e.g. non-timeout failure marked as timeout), issue a new SHA-256-bound correction receipt that names and binds all originals, records the exact contradiction, and supersedes only the incorrect field. Do not modify, overwrite, or retry the original producer. Obtain fresh independent review on the correction pair. See `references/immutable-correction-receipts.md`.
- **Read-only champion/challenger governance audit**: for model governance audits, trace the complete path from inferred/runtime champion identity through registry declaration, checkpoint hashes, aliases, source snapshots, challenger comparison receipts, admission gates, and any apply/promotion surface. Do not stop at flags named `promotion_allowed=false`: prove the binding and semantics. Test for path/hash cross-binding, incomplete ensembles classified as confirmed, top-level `PASS` masking `HOLD`/`REJECT`, missing equal-weight/same-universe/cost/no-lookahead controls, stale aliases or source dates, and “apply ready” states coexisting with promotion `NOT_READY`. Use the detailed checklist and reproductions in `references/champion-challenger-governance-audit.md`. Run focused tests with an external basetemp when the repository hardcodes a generated-root basetemp; report collection/setup failures separately from behavioral results. Never edit, train, write model artifacts, mutate a registry, or promote during this audit.
- **Cron safety harness for governed unattended execution**: when moving a manually-operated governed system (paper-evidence pipeline, daily loop, research batch) to cron-scheduled unattended operation, build a Layer 0 preflight *before* wiring any cron job. The five components, in order: (1) a frozen `CronTaskEnvelope` dataclass (job_id, authority_class, allowed_tools, stop_condition, run_lock_path, receipt_path) that every job must construct and serialize before doing work; (2) a file-based `RunLock` using `os.O_EXCL` atomic create, with stale-lock detection (timestamp-based, configurable max age) and non-blocking acquire (returns False, not hang); (3) a `NoSubmitGuard` that reads the board's execution-interpretation field from both `PROJECT_ADVANCEMENT.md` (regex) and `docs/VESPER_FACT_BASE.json` (structured), merges them (fact-base overrides markdown), and hard-fails if interpretation is not `bounded_paper_order_evidence_only` or if `paper_execution_scope` is not `paper_only` — fail-closed on missing/malformed files too; (4) a `CronReceipt` frozen dataclass with status `PASS`/`FAIL`/`HELD`/`BLOCKED`, where PASS requires evidence_path and rejects errors, FAIL requires an error, and started_at must precede finished_at; (5) a `scripts/cron_dry_run.py` harness that chains all four: build envelope → acquire lock → assert guard → (simulate work) → write receipt → release lock → print summary. Test the failure paths too: lock conflict produces HELD receipt + exit 1; safety violation produces BLOCKED receipt + exit 1. Only after the dry run passes should Layer 1 (actual cron wiring) begin. Layer 1 wraps real entry points (`run_daily_paper_evidence_loop.py --no-submit`) in the same harness and wires them as `no_agent=True` cron jobs via thin `.sh` wrappers under `~/.hermes/scripts/`. Layer 2 adds a `CrossSystemStatus` aggregator that reads Layer 1 receipts/status/alerts and renders a read-only health panel in the operator terminal via a `cross-system` command. The progression is Layer 0 (preflight proof) → Layer 1 (cron wiring) → Layer 2 (unified operator surface) → Layer 3 (cross-system triggers + alerts) → Layer 4 (guarded continuity). See `references/cron-safety-harness.md` for the full pattern, code shapes, Layer 1/2 implementation details, test patterns, and the Layer 0→4 progression used in Vesper.
- **Team knowledge versus runtime journals for multi-agent crons**: separate reviewed knowledge from operational event history. Durable, reviewed worker knowledge belongs in versioned documents such as `.hermes/workers/<name>.md`, with evidence dates and accepted/proposed/superseded states. Append-only files such as `.hermes/learnings.jsonl` or `team_memory.json` often accumulate cycle IDs, timestamps, quota state, database dates, scheduler results, usernames, machine paths, dirty-worktree counts, and repeated status; treat those as generated runtime state by default and keep them ignored/untracked. If a project intentionally versions a shared journal, curate and redact entries before staging, strip machine/user identity and transient telemetry, and commit only stable discoveries—not raw scheduler cycles. Never infer that a JSON/JSONL filename is durable knowledge merely because agents read it.

## Workforce Skill-Capacity Documentation

When a governed repo uses named workers and specialist pods, treat skills as capability profiles rather than new authority-bearing agents. Record the hierarchy, pod assignments, lane ownership, skill progression, and approval boundaries in a durable project document, not only in chat. A single successful task is experience, not a skill. Five correct, receipt-backed repetitions across meaningful variations create a promotion proposal; they do not self-promote the capability. Promotion requires independent review, a dated accepted-knowledge entry, and explicit routing review. Skill growth must never widen broker/order, model-promotion, risk, scheduler, provider, secret, or approval authority.

For Vesper-style work, link the worker knowledge README to `docs/WORKFORCE_OPERATING_MODEL.md`; keep individual `.hermes/workers/<name>.md` files for accepted/proposed/superseded knowledge and evidence dates. When a user explicitly says they cannot reliably remember operating decisions, update the durable project model during the same session and report the path.

### Capability-ledger implementation pattern

When implementing worker skill growth, use an append-only, hash-verified capability ledger rather than a counter or mutable profile. Register a versioned skill definition with scope, non-goals, allowed scenario classes, minimum passes, and minimum scenario diversity. Record every attempt with worker, skill version, scenario class, stable task ID, input/output receipt references, outcome, timestamp, and critical-failure flag. Retain failures; add explicit reviewed resolution events rather than deleting or rewriting them. Record independent reviews against concrete attempt IDs. Evaluate promotion eligibility fail-closed: require the pass threshold, varied scenario coverage, at least one independent review, no unresolved critical failures, and valid skill scope. Detect malformed or tampered ledger events by validating event hashes before evaluation. Keep `eligible_for_promotion` separate from `accepted_skill`, and keep both separate from broker/order, model-promotion, risk, scheduler, provider, secret, and approval authority. If the repo has an operator terminal, expose a read-only evaluation command and test RED→GREEN with focused tests before wiring the surface.

## Evidence-Backed Repair Documentation And Review

- Every repaired defect in a governed Vesper session should get an issue-ledger entry in `docs/ISSUES.md` with a stable `VQ-YYYYMMDD-NNN` ID, severity, status, exact component, reproduction evidence, remediation, focused verification counts, and authority impact. Never include credentials or sensitive account identifiers. Mark `Verified closed` only after the new regression and adjacent contract tests pass.
- Independent review is fail-closed on input quality. Send the complete unified diff (`git diff -- <scoped files>`) plus the exact review criteria—not a prose summary or file-level change list. If the candidate includes untracked files, ordinary `git diff` is empty: freeze and SHA-256-bind every candidate file, build its exact review diff with `git diff --no-index /dev/null <path>`, and require the reviewer to verify those hashes first. If the reviewer rejects the input as unparseable or incomplete, rerun with the full diff before treating it as a code verdict.
- Freeze the final staged candidate before dispatching final reviewers and identify it with a staged-diff SHA-256 or staged tree ID. Do not continue editing in parallel with final review. Any staged change after dispatch invalidates that verdict; rerun the affected gates and obtain a fresh review of the new identifier before commit/push. **A request to “continue” does not relax a live review freeze: perform only read-only preparation until the verdict. If a known defect requires an urgent repair, explicitly supersede the frozen review as no longer attributable, then repair a successor candidate and dispatch a fresh reviewer.** See `references/large-dirty-worktree-curation.md`.
- When a repository has a global pytest basetemp under `artifacts/`, remove that repository defect and run focused suites with a unique external temp root. Separate repository configuration failures from machine-local Windows ACL failures; do not alter ACLs or delete shared temp directories as a workaround without approval.

## Fresh Verification After Context Handoffs

When curating an explicitly authorized broad dirty worktree, follow `references/large-dirty-worktree-curation.md`. It covers classification before staging, complete-diff secret scanning without stdout truncation, project-test isolation from inherited `PYTHONPATH`, portable logout-safe Windows task definitions, and safe retirement of duplicate schedulers.

When a system or handoff reports stale failed verification after code edits, do not rely on the old output and do not immediately rerun the entire repository suite as the only gate. First run the smallest changed-path pytest slice with an explicit external `--basetemp`, then run adjacent contract tests, `py_compile`, and `git diff --check`. Read the fresh failure output before editing. If the full suite later times out or contains unrelated failures, report that boundary separately; do not downgrade fresh focused green evidence or claim the full suite passed. This is especially important for Vesper's operator-terminal/controller/VOT changes, where focused suites can prove the repair while the broad repository suite is too slow or noisy to finish in the session.

 If pytest fails during fixture setup because a Windows temp root or stale repo-local basetemp is access-denied, first rerun the affected slice with an explicit external `--basetemp` path. Do not change ACLs or delete shared temp state automatically. If the external run passes, classify the original failure as environment/setup evidence, not a source regression.
- **Do not claim full verification from focused green tests.** Report focused suites, full-suite results, skips, failures, and infrastructure termination separately. A full run that exits nonzero (including a terminal-control/exit-139 condition) is not green even when the changed slices pass.
- **Reconcile validators against the current workflow before restoring retired requirements.** Read the active workflow and current operator architecture. If a validator still requires retired Node/React/cockpit commands after a terminal migration, remove only those stale requirements and preserve stable command prefixes so older valid fixtures remain accepted. Do not restore retired surfaces merely to satisfy a stale validator.
- **A global pytest basetemp under `artifacts/` is a repository bug.** Keep pytest scratch space outside generated evidence directories; CI may provide an explicit external path, while local configuration should avoid forcing a machine-specific or artifact-owned path.
- **Concurrent issue-ledger edits need preservation, not replacement.** If `docs/ISSUES.md` changes during an agent pass or enters a conflict state, preserve both the operator's entries and the agent's evidence-backed entries, remove only conflict markers, then re-check `git status`, `git diff --check`, and the final issue headings before reporting documentation complete.
- **Never restore a dirty file from `HEAD` to recover an edit.** In a broadly dirty governed worktree, `git show HEAD:<path> > <path>` destroys unrelated uncommitted user changes in that file. Before touching a dirty target, capture its exact pre-edit content (or use a temporary copy/worktree), apply minimal unique-context patches, and compare the final diff against the captured baseline. If a patch matcher reports repeated/ambiguous text, stop and re-read the full file; do not retry with `replace_all=True` against common fragments, because it can corrupt multiple functions or module headers. Prefer anchors containing the enclosing function/class and verify syntax immediately after each repair.
- **Approval workflows require authenticated principals before `approval_granted=true`.** Use an append-only, hash-bound request/decision ledger with explicit actor, scope, reason, expiry, and decision fields. Replaying malformed or tampered events must fail closed; expired or already-decided requests cannot be decided again; enforce separation of duties (no self-approval). However, caller-supplied names, CLI arguments, environment variables, and strings such as `brennan`/`thomas` are labels—not authenticated identities. Until the system binds each principal to a trustworthy OS/session signature or other authenticated credential, decisions may be recorded only as attestations: keep `approval_granted=false`, `execution_authorized=false`, and make every execute/apply path fail closed. Do not add an approval-backed dispatcher merely because two distinct labels appear in the ledger. Once authenticated identity exists, an `APPROVED` record may mean that the exact requested action and scope were granted; downstream execution must still independently revalidate current authority, exact action/scope binding, freshness, market/session, risk, idempotency, and all other safety gates. Unsupported broker/order, promotion, scheduler, target/risk, provider, and secret actions remain closed until separately governed handlers exist. Surface this distinction plainly in terminal labels and help text.

- **Proposal-ledger source and approval binding:** a planning-proposal generator must consume a deliberately audited, pure local source—not a convenient operator/dashboard snapshot until its complete transitive dependency graph is proven free of provider/account reads, cache writes, and other side effects. Bind each proposal deterministically to the normalized source snapshot digest and classify before any route. Persist gated/ambiguous proposals only in the local ledger; never put them in a runnable board state merely to make them visible. Reuse one append-only approval/attestation record across desk and mobile surfaces, binding proposal ID and source digest in its exact scope. If authentication is absent, both surfaces must display the same non-authorizing attestation rather than inventing a second approval mechanism. Freeze all tracked and untracked candidate files before independent review: stage the exact allowlist, require no tracked unstaged diff in it, capture base SHA, staged tree, and a SHA-256 digest built from the complete staged binary diff; do not edit while that review runs. After any verification-status warning, rerun the narrowly affected tests against the frozen tree and re-check the recorded digest before reporting it verified.

## Pitfalls
: when asked to "parse the project and see what makes sense," measure:
  (1) ratio of governance code to product code
  (2) whether receipt chains produce evidence or just review prior receipts
  (3) whether tests can actually collect (missing deps = blind spots) — this is your leading indicator
  (4) whether board/truth files are readable (size vs. signal ratio)
  (5) whether the strategic goal is advancing or stalled
  Report structurally — "what makes sense" vs "what doesn't" — with file counts, line counts, and specific field citations. Don't sugarcoat: if the chain produced 123 receipts all saying `empirical_model_skill_proven: false`, say so.

  **Prioritization framework**: after measuring, rank recommendations by risk/impact using a 3-tier system:
  - **🔴 Tier 1 — Blockers that invalidate other work**: test collection errors (means no evidence from any test-run is trustworthy), broken imports, authority-gate contradictions. Fix these first — everything else is built on sand.
  - **🟡 Tier 2 — Structural work that unlocks progress**: model-evaluation blockers (e.g. `insufficient_confirmation_windows`), framework migration (reduces tech debt and surfaces bugs), weekly tuning packets (adjusts live knobs based on evidence).
  - **🟢 Tier 3 — Productivity & visibility improvements**: GUI dashboards, reference docs, data expansion work. Valuable but not blocking.
  - **🔵 Tier 4 — Long-term bets**: source-switch prep, alternative data feeds, model training infra. Worth flagging but don't recommend as immediate action unless the user asks.
  Explain WHY each tier — "fixing test collection first means every subsequent test result is trustworthy" vs "the GUI is nice but doesn't change the model's output."
  
  **Date-awareness for trading systems**: before recommending work on a trading/quant project, check what date it is and whether markets are open. The pattern:
  - Weekend (Sat-Sun) → "between-closes" territory. Flag that the next trading day is Monday. Daily paper-evidence loops can't submit orders, but between-closes work (tuning, framework migration, test repair, dashboard work) is the right lane.
  - After-hours on a trading day → same-day paper evidence can still be collected (fill/position evidence), but new order submission is gated to market hours.
  - During market hours → paper order submission may be actionable if the board's execution window allows it.
  Always state the current date and day-of-week in your recommendation context so the user knows you accounted for it.

## Pitfalls

- **Golden/file-test TDD has two intentional RED states.** First add only the minimal source fixture and run it before production changes; confirm it fails because of the bug, crash, or unexpected success—not because the fixture is malformed. After the fix, rerun and inspect that the remaining failure is only stale generated output. Then use the repository's autoupdate tool rather than hand-writing generated `CHECK`/snapshot blocks. Finally run both the focused test and the shared all-file-tests target: corrected recovery often changes an existing malformed-input fixture in addition to the new regression test, and that intentional delta must also be autoupdated and reviewed.
- **Uncommitted session work vanishes on topic shift.** `patch`/`write_file` edits only exist in the working tree. When the conversation compacts, switches topics, or hands off, there is no automatic commit — any unstaged changes are effectively lost. This differs from human workflows (where the same IDE session continues) because Hermes sessions are discrete: a new prompt or compaction discards the agent's awareness of uncommitted work. **Fix:** after every coherent set of changes, commit immediately (`git add <file> && git commit -m "short message"`) before moving to the next topic. Auto-commit governance (when allowed per repo rules) should be actively used, not deferred. If you gave the user status indicators like TODO items marked complete, nothing warns them the file patches never made it to git. The only way to detect lost work retroactively is cross-referencing `git log` against `session_search` — don't create that situation.
- **Session-level hard rules override repo defaults.** A repo's governance may say "commit and push by default" but if the session prompt says "do not edit, do not commit, do not push" — the session rule wins because the human's direct instruction takes priority over the project's written defaults in every case. Never infer permission from the repo when the session explicitly forbids the action. Flag the deviation ("repo default says push, session says don't — not pushing") and stop. This is the single most important pitfall: it applies even when the repo governance is fully understood and the work is safe by repo standards. A read-only comprehension test where the session prompt imposes "Do not edit files. Do not stage, commit, push" is a distinct task shape — the pre-action safety report IS the deliverable, not a preamble to action. Only proceed past the report if the prompt explicitly says to execute; otherwise the report is the final output. Silence after a report is not consent to proceed.
- **Read-only comprehension tests are a distinct task shape.** When a prompt asks you to read files and answer questions with "do not edit" constraints, the pre-action safety report IS the deliverable — not a preamble to action. Do not "proceed if safe" unless the prompt explicitly says to. Write the report, cite filenames and exact fields, and stop.
- **Governance ouroboros: receipt chains can consume the project.** When a governed repo has 49 near-identical scripts and 123+ receipts all saying `empirical_model_skill_proven: false`, the governance infrastructure has become the work itself rather than guarding the work. When assessing a repo, check whether the chain is producing evidence or just reviewing prior receipts. The right response is to surface this to the human, not generate more receipts. **The escape hatch: run the project's actual model pipeline.** In Vesper, `scripts/run_daily_paper_evidence_loop.py --date <YYYYMMDD> --symbol AAPL --side buy --notional 5.00 --no-submit` is the allowlisted preview command that actually generates real model decisions with fresh data. It reveals whether the model is alive, what basket it's selecting, and whether board data dates are stale (board says OHLCV=06-18, real data=07-02). The no-order report is the first real evidence receipt — use it as a board cross-check before generating more governance receipts.
- **Board drift detection**: trusted values in the board's Current State section (data freshness dates, selected basket, OHLCV dates) can be stale. Cross-check against actual output from the model pipeline (no-order report, paper evidence loop). A board that says OHLCV is at 2026-06-18 when real data is at 2026-07-02 means the board hasn't been updated since the last data refresh — the model is working but governance tracking lagged.
- **Real evidence beats governance evidence**: when asked to "start building the project" or "work on a model," prioritize running the actual model pipeline over generating more chain receipts. Factor IC analysis on real data (Spearman correlation between features and forward returns) is the lowest-cost, highest-value quant research entry point — it tells you which features actually predict returns, replacing hardcoded `rank_ic_floor: 0.02` placeholders with measured values.

Then run tests with the Hermes venv Python: `"$HERMES_VENV/Scripts/python.exe" -m pytest ...`. Target: zero collection errors.
