# Governed Repository Workflow Map Delivery

Use this reference when a user requests a complete current-repository workflow diagram delivered as a desktop document artifact.

## Evidence-first source inventory

Read the current-state board, repository policy, pipeline map, operator-surface contract, autonomy/workforce documents, and manifests. Label each claim as active/evidence-producing, tracked/implemented, configured, proposed, or historical/compatibility. Do not turn a roadmap, test fixture, isolated-worktree candidate, or scheduler configuration into a live claim.

## Diagram coverage standard

The main diagram must cover governance/source hierarchy, human authority, software-delivery/review lifecycle, control plane/tasks/worktrees/receipts, data → factors → portfolio/admission → paper/research flow, operator surfaces, scheduler/watchdogs/CI, storage/evidence, current/proposed autonomy stages, and strict authority boundaries.

“Complete” means include every top-level tracked repository area and operational domain. Do not force every file into the SVG: add a detailed tracked-top-level inventory with path, count, role, and active/retained/proposed status.

## Document requirements

- Deliver a standalone offline HTML with inline SVG/CSS, no action controls, credentials, scripts, or network requests.
- Place a linked Table of Contents directly below the diagram.
- Add an explicit source-hierarchy/authority disclaimer.
- Validate HTML parsing, unique IDs, and every TOC anchor.
- Obtain independent content/governance review before submission. If visual capture cannot be obtained, report structural validation accurately; never claim unperformed visual QA.
- Treat a Desktop copy as a distribution artifact; preserve source/repo state separately.
