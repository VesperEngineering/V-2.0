# Vesper Kanban Operations

Use when reading, approving, unblocking, archiving, or triaging cards on the Vesper Hermes kanban board, or when wiring approval flows that touch it.

## Board layout

- DB: `~/AppData/Local/hermes/kanban/boards/vesper/kanban.db`
- Tables: `tasks`, `task_comments`, `task_events`, `task_links`, `task_runs`, `task_handoffs`, `task_attachments`
- **Reads:** direct read-only SQLite (`sqlite3.connect(f"file:{db}?mode=ro", uri=True)`) — instant, no subprocess. This is what VOT does at 500 ms poll. For a coherent multi-table audit, begin one read transaction and query tasks, links, comments, events, runs, handoffs, and attachments through that same connection.
- **Do not add `immutable=1` to a live WAL-backed Kanban query.** Immutable mode promises SQLite that the database cannot change and can omit current uncheckpointed WAL state. Use `mode=ro` for live truth. If the audit requires a byte-stable frozen snapshot, use an approved snapshot/copy of the database together with its `-wal` and `-shm` companions, then query the copy and record the snapshot time.
- **Writes:** ONLY via `hermes kanban` CLI verbs — they record audited history (comments + events). Never write the DB directly.

## CLI pitfalls (all hit live)

- **`--board` goes BEFORE the verb:** `hermes kanban --board vesper list`. Placing it after (`hermes kanban list --board vesper`) errors `unrecognized arguments`.
- **There is no `delete` verb** — use `archive` (history is preserved in `task_events`).
- **`unblock --reason "<text>"` records the reason as a comment before unblocking** — the right way to attach an approval receipt to the state change.
- **Neither `blocked` nor `triage` is an unconditional human-review gate in current Hermes Kanban.** Live verification showed `--initial-status blocked` writes no manual `block_kind`, so the dispatcher can emit `promoted` and move it to `ready`. The installed CLI parks a card with `--triage` (not `--initial-status triage`), but official Hermes docs and gateway source show `kanban.auto_decompose: true` by default: each dispatcher tick may decompose/specify a triage card, create children, promote work, and dispatch workers. Therefore, never represent a proposal as safely awaiting human review merely because its task status is `blocked` or `triage`. Do not implement `create blocked` followed by `block --kind needs_input` as a workaround—the two CLI writes are non-atomic and leave a dispatch race.
- **Use a separate proposal ledger for a durable approval boundary.** Generate and persist bounded, idempotent proposal packets outside the runnable Kanban task table; surface them in both VOT and Telegram. Only an authenticated, exact-scope human approval should create/promote the corresponding Kanban work card. If a task is intentionally placed in triage for ordinary decomposition, label it as decomposable work—not a human approval hold—and read the live `kanban.auto_decompose` configuration before predicting its behavior.
- **Keep any Kanban publication idempotent without reissuing mutation blindly.** Before `create`, look up the exact idempotency key read-only under a process lock. Search terminal **and archived** rows: Hermes create-time dedup reuses only a non-archived matching key, so an archived match can otherwise be silently duplicated. If a match exists, reconcile its task ID/status/assignee/creator/parent set and issue no create; reuse the exact lineage unless a deliberately versioned successor is required. After a first create, read the authoritative row and event stream back; malformed, ambiguous, unexpectedly promoted, or auto-decomposed outcomes are unknown/fail-closed. See `references/human-review-gates.md` for the current CLI/docs/source evidence and isolated probe recipe.
- **An unassigned runnable card is not inert.** If `kanban.default_assignee` is configured, the dispatcher can assign and spawn a `ready` card whose create event recorded `assignee: null`. Never use `assignee=None` as a single-writer or human-hold control. Read the live global Kanban config and use a real dependency gate, a non-runnable proposal ledger, or a deliberately blocked/parent-gated aggregator whose release is separately controlled.
- **`comment` takes positional text:** `hermes kanban comment <task_id> "text"` (no `--board`, no `--text`).
- **`complete` supports only `--result`, `--summary`, and `--metadata`:** put test commands/counts inside the structured summary or metadata. Do not pass unsupported standalone `--test-command` or `--tests-passed` flags.
- **A loop-breaker `triage` card is not ordinarily closable.** Current CLI behavior rejects `promote` because it accepts only `todo`/`blocked`, and rejects `complete` while the card remains `triage`. Do not call `specify` or `decompose` merely to force an already-reviewed implementation through closure: those LLM paths may rewrite scope or create duplicate children. Record the acceptance receipt, preserve the verified artifacts, inspect the exact event/child graph, and use only an explicitly supported state transition; never patch Kanban SQLite directly. Prevent this dead-end by representing a first review handoff once and avoiding repeated same-kind unblock/re-block cycles that trigger `block_loop_detected`. If no supported non-rewriting transition exists in the installed CLI, report the board-state blocker separately from code acceptance rather than claiming the dependency was released.
- **A failed multi-command closure sequence may still have partial side effects.** If `comment` succeeds and a later `promote`/`complete` fails, read the card back before retrying. Preserve the valid receipt and do not append duplicates or assume the child dependency was released.
- **`kanban show` can crash** with `TypeError: 'str' object cannot be interpreted as an integer` when a card's `created_at` was written as a literal string (a known writer defect, e.g. `'%s'`). Recovery: read the card and its history via read-only SQLite on `tasks` / `task_comments` / `task_events`. Do not conclude the card is unreadable — only the renderer is.

## Provenance before action (FIRST-CLASS rule)

Before acting on any blocked / `needs_input` card, read its `task_comments` history. The operator's standing instruction may already exist there, and the card's current title/body may not represent the original request.

## Project and version isolation

A board is an execution boundary, not merely a visual view. When a user operates a new generation of a project alongside a legacy repository, create a dedicated board and do not treat the legacy queue as the new system's backlog.

1. **Establish the boundary before scheduling work.** Create a dedicated board with the new project's canonical root as its default workdir. Create or verify a dedicated implementation profile; set its intended model/provider explicitly and verify its configured credential resolves.
2. **Do not infer migration from related names.** Inspect nonterminal legacy cards first. Recreate or reassign a task into the new board only when the operator has explicitly approved that exact new-version scope. A legacy task's `todo`, `ready`, or `blocked` state is never authorization to execute it in the new project.
3. **Keep authority sources version-specific.** The new project's `AGENTS.md`, coding constitution, and data/safety boundaries control its cards. Legacy rules, model gates, and scheduler procedures are reference-only unless the new project explicitly admits a source or artifact.
4. **Telegram groups are not profile routing.** A focused Telegram group is a conversational workspace; Kanban dispatch runs the assigned Hermes profile. Do not claim that creating a group automatically creates, configures, or routes a worker profile. Verify both surfaces separately.
5. **Use workday controllers as observers, not authority escalators.** Weekday kickoff, periodic controller, progress brief, and closeout jobs may read the dedicated board and report status. They must not create, promote, unblock, reassign, or dispatch cards just to make the queue look active. When no approved cards exist, report that the worker is standing by.
6. **Verify natural activation.** After scheduling a controller, confirm the gateway heartbeat is healthy and read back the first naturally scheduled run's status and stored output. A created cron definition alone is not proof that the workday loop is active.

### Retiring a legacy board during a version cutover

When the operator explicitly retires an old project generation, treat it as a controlled shutdown—not a migration shortcut.

1. **Create and verify the replacement boundary first.** Create the new-generation board with its canonical workdir and dedicated profiles. Do not reuse legacy profile names, prompts, or authority rules as the new system's defaults.
2. **Do not migrate cards by implication.** An old card's title, state, assignee, or apparent relevance is not approval to recreate it in the new board. Start the new board empty unless the operator explicitly approves each task scope.
3. **Pause legacy job ownership before archiving the board.** Inventory every enabled cron/script/agent job that can read, create, mutate, dispatch, or report legacy work. Pause those jobs and read back `enabled=false` before archiving the board, so a still-running bridge or dispatcher cannot recreate work during the cutover.
4. **Archive rather than hard-delete by default.** Use `hermes kanban boards rm <legacy-slug>` without `--delete`; it preserves receipts/history under `_archived/` for recovery. Hard deletion requires an unambiguous operator request to destroy that history.
5. **Reset shared routing after the old board is gone.** Verify `kanban.default_assignee` names a valid new-generation coordinator or is empty. A legacy fallback can silently claim a new unassigned card.
6. **Verify all planes.** Read back active boards, enabled cron jobs, nonterminal tasks, current board, and gateway health. Report separately that project files remain preserved unless the operator specifically ordered repository deletion.

### Staffing and task-order preflight

Before recommending subagent staffing, a new audit wave, task decomposition, or an execution order, inspect the live board—not only architecture documents, test output, or a task title:

1. Read the tracker header for program context, then query every nonterminal candidate card and its parents, children, dependencies, comments, and events through the read-only database.
2. Identify original operator provenance. `REJECTED`, `delete/remove`, `stop`, and exact-scope denials outrank a later title rewrite, automatic promotion, or generic VOT `UNBLOCK` comment.
3. Classify each candidate as valid new work, a stale descendant, or an auto-decomposition of a rejected/failed ancestor. Do not propose parallel work that piles onto a stale lineage.
4. For runtime/operational work, inspect live scheduler and receipt state independently. Tests, docs, task labels, `Ready`, and zero exit codes are supporting evidence—not operational proof.
5. State the exact task IDs and evidence sources used. If this preflight was not performed, label the recommendation a generic pattern rather than current-task advice.

When provenance conflicts: preserve receipt/history, terminally reconcile or archive the rejected lineage, repair any resurrection path if needed, and only then create bounded audit or implementation work. Do not ask a reviewer to validate or freeze an execution that correctly did not occur.

Real case (t_cf7ed479, 2026-07-19): a junk card titled `good` was correctly flagged inadmissible, the operator commented "REJECTED" then "remove task from queue. Delete it.", and the **auto-decomposer later rewrote it into a plausible-looking spec-elicitation card** that sat blocked for 51h firing alerts. Acting on the current body (asking the operator to "answer the spec questions") would have been wrong; the comments showed the standing delete instruction. The auto-decomposer can resurrect junk into spec-shaped cards — verify origin via comments before treating a card as real work.

## Recording operator approvals (receipt-backed)

When the operator approves a card in chat (e.g. "approved"):

1. Record the approval as a kanban comment carrying: approver, date, source surface, and the EXACT scope — including what remains denied.
2. Then `unblock --reason` with the same scope text, so the state change and receipt are one auditable event.
3. Never widen scope beyond the card's written text. Blanket approvals do not cascade to other cards or to gated classes.

## Dual approval surfaces (operator policy)

The operator wants BOTH surfaces live, neither exclusive:

- **VOT (desk, primary):** kanban panel writes via the `hermes kanban` CLI with status gates and inline confirmation; formal approval ledger in `app/services/vot_approval_workflow.py`.
- **Telegram (mobile):** the gateway agent runs the same CLI verbs against the same board; VOT sees the change on its next poll.

Gated classes — broker/order, risk, scheduler, promotion — stay human-gated on EVERY surface. Telegram is an additional way for the operator to exercise existing authority, never a widening of it. Phone approvals keep the same exact-scope + receipt discipline. Kanban decisions made via Telegram do not auto-create `vot_approval_workflow` ledger entries; that ledger flow is VOT-side.

## Goal-loop implementation lifecycle

Use this when a user asks Vesper to work through a roadmap or when a safe implementation goal should run autonomously.

1. **Create a bounded goal, not a vague reminder.** Search the board first for duplicates. Use `--goal`, an idempotency key, a worktree, bounded turns/runtime/retries, and a body containing: objective, acceptance evidence, hard exclusions, source-of-truth paths, and dirty-worktree handling. Before adding forced `--skill` values, prove those exact names resolve in the assignee profile; an unknown forced skill can crash the worker before it reads the card. Also verify both profile `agent.max_turns` and card `--goal-max-turns` are positive.
2. **Verify dispatch state instead of assuming it.** A goal may return `ready`, auto-start between commands, or remain queued behind profile/concurrency limits. Recheck `show`, `runs`, `log`, `stats`, and the relevant list entry immediately after the first dispatch; a dry-run dispatch is only a candidate snapshot, not proof of actual spawn cardinality. When the operator asks to start one specific ready task while others are ready, first confirm the exact task is the first eligible candidate and verify the installed dispatch cap semantics; after the real dispatch, require the returned spawned task ID and `show`/run state to match that exact task, with no unrelated task started. If startup fails before mutation, record the root cause, verify the worktree is clean, archive the failed card, and create one corrected replacement rather than replaying the same invalid configuration.
3. **Model parallel audit dependencies in the correct direction.** `create --parent P` makes `P` a prerequisite of the new card. Do not make a running coordinator goal the parent of audit cards it needs; those audits will wait for the goal. Create parallel audits unparented with the coordinator ID in their provenance, then make the later synthesis/integration card depend on the audits. See `references/parallel-goal-coordination.md` for the full coordinator/auditor pattern, failure recovery, and Windows worktree-path preflight.
4. **Treat `blocked`/`needs_input` as a review handoff.** Read the actual worker worktree and its comments. Do not accept a self-reported implementation without inspecting source, tests, generated evidence, and the diff. Run the focused tests independently in the worktree and then again in the canonical branch. For a fail-closed persistence claim, seed a structurally valid state store with malformed values (for example, an invalid timestamp or embedded JSON), then exercise the complete status-and-receipt path. A corrupt database-file test alone does not prove parser failures are contained.

   **Early read-only review while a goal is running:** A board heartbeat proves liveness, not correctness or a completed handoff. When an active worktree already contains source/tests, inspect it read-only but never patch, stage, or run write-producing tests inside that worker's worktree. If you find a potential fail-closed gap, reproduce it in an isolated temporary root first. Then add a concise Kanban comment naming the malformed input/state, required safe behavior, and exact regression test. This lets the worker repair the issue without a race and preserves an auditable review trail.

   **Single-writer takeover after timeout/block:** A terminal `task_runs` row or a `blocked` card does not prove the spawned Hermes process exited. Before editing an inherited worktree, pause any task-scoped supervisor, prevent redispatch of the exact card, and inspect both board runs and the host process tree. Attribute a suspected writer by exact command line (`work kanban task <TASK_ID>`), executable, PID, parentage, and start time; do not kill the gateway parent or an ambiguous process. Snapshot the tracked binary diff and intended untracked implementation files outside the repo, then try a polite process-tree stop and force only the proven stale task tree if needed. Verify the PIDs are gone and sample relevant file hashes twice across a short interval before declaring one writable owner. If patches report “file modified since read,” stop stacking edits and repeat this ownership check rather than treating the warning as ordinary patch drift.
5. **Promote only the intended source.** Stage only reviewed source/tests/docs. Never stage runtime ledgers, basetemp directories, fixture output, secrets, or unrelated dirty files. Commit in the worker worktree if useful, then cherry-pick the exact commit into the canonical branch; verify the canonical diff and rerun tests after promotion.
6. **Close with an exact-scope receipt and a dependency-release preflight.** Before completing a coordinator/parent goal, inspect every direct child and dependent. Parent completion may immediately promote and spawn previously blocked children—even cards already documented as superseded. Unlink or terminally reconcile superseded children before closing the parent. If a child is released and already `running`, reclaim that exact task first, verify the claim/process is released, then complete it individually; `--summary` and `--metadata` are per-task and bulk completion with those fields is rejected. Add a Kanban comment naming the reviewer, commit, tests, fixture evidence, and denied capabilities. Complete the card with `--result`, `--summary`, and structured `--metadata`. Do not mark a real-provider canary as passed when the transport is intentionally blocked.
7. **Advance one slice at a time.** Only launch the next roadmap goal after the prior card is integrated and closed. Keep provider, broker/order, risk, promotion, scheduler, and secret authority separately gated even when the outer control loop becomes autonomous.
8. **When the user expects hands-off continuation, install a bounded task supervisor immediately.** A conversation turn is not durable supervision. After dispatching one bounded goal, create a short-lived cron supervisor scoped to that exact task ID and terminal closure only (for example, every 2 minutes with a finite repeat count). Its prompt must: inspect active worktrees read-only; comment and unblock only exact fail-closed rework; independently validate a blocked handoff; commit/cherry-pick only reviewed files; close the card with a receipt; resolve duplicate auto-decomposition through CLI; and explicitly forbid launching the next roadmap slice. **Pin the supervisor to the active session's known-working model/provider when creating it; do not leave routing implicit.** Immediately trigger one real tick, then inspect the job's `last_status`/execution result before claiming autonomy. For a recurring supervisor use recurring schedule syntax such as `every 2m`; a duration such as `2m` is a one-shot delay even when a repeat count is supplied. After the probe, verify `enabled`, `state`, `next_run_at`, and the repeat counter—manual execution of a one-shot can consume and disable it, so update to the recurring schedule and re-enable before relying on cadence. A successful `create` response proves only scheduling, not that the agent can run; if the probe exposes a routing failure, update the job's explicit model/provider and rerun the probe before relying on its cadence. In the local TUI, explain once that `deliver=local` keeps its output stored rather than unsolicited in-chat; this is not a reason to make the user keep prompting.

### Standing `/goal` versus Kanban goal mode

Treat these as two independent coordinators, not two views of one lifecycle:

- A standing `/goal` is persisted in SessionDB under `goal:<session_id>`, judged after conversation turns, and can park on a process/session/time barrier. It may stay active while a related Kanban card is blocked or terminal.
- A Kanban `--goal` loop belongs to an ephemeral dispatcher worker. Its budget is also bounded by the assignee profile's `agent.max_turns`; the effective ceiling is the earlier of that profile limit and the card's `goal_max_turns`. A larger card budget does not prevent a lower profile budget from producing `gave_up` first. Kanban goal mode has no standing-goal wait barrier; a judge `WAIT` is treated as `CONTINUE`.
- A `created_by=hermes-standing-goal:<session>` string is provenance only. It does not bind card state, worker ownership, or completion to the standing goal automatically.
- Choose one writer. If the standing goal is coordinating, do not also expose a ready Kanban root that can be default-assigned and spawned against the same worktree. Keep the board root parent-gated as the final aggregator, let bounded implementation/review cards feed it, and re-read the board plus standing-goal state before every release.
- Dependency direction is operational, not visual hierarchy: `parent -> child` means the child waits for the parent to finish. A root that needs its work cards must depend on the final leaves (`leaf -> root`), not be their prerequisite (`root -> first work card`), or the graph deadlocks.

See `references/session-2026-07-21-standing-goal-kanban-split-brain.md` for the live provenance pattern, deadlock repair order, and duplicate-safe card registry.

### Goal-loop pitfalls

#### Real-worker canaries require an admissibility gate

A real card, real worker, terminal `done`, plausible candidate, and deterministic `ACCEPTED` result still do not prove an admissible loop. Before allowing receipt closure or an unattended schedule, independently bind and read back the contract, task/run/worktree/branch/HEAD/assignee, exact persisted project ID (not merely the CLI selector), exact retry/runtime limits, observed tool telemetry (including failed calls and resolved paths), declared content-hashing profile, frozen inputs, evaluator result, event chain, consumed limits, and review state. Count model turns and tool actions from the persisted worker session rather than a log footer's aggregate message count, and account explicitly for Git LF/CRLF filtering when binding text hashes across worktrees. Any non-allowlisted tool or dependency acquisition, `dir` workspace when a worktree was required, retry widening, task identity overwritten by a candidate hash, unverified consumed limits, or lifecycle `CLOSED` before exact independent approval is `HELD`. Preserve failed attempts and issue a new idempotency identity rather than rewriting evidence. Treat each independent-review `HOLD` the same way: a successor approval requires a fresh reviewer task, clean worktree, and fresh pending receipt bound to that reviewer—not an unblocked/reused held card. Preallocate a real reviewer task ID without making the card spawnable: an assigned `--initial-status blocked` card is not a safe reservation because dispatch can promote it. If the gateway is stopped, verify the ready queue before a bounded manual dispatcher pass and require the returned spawned task ID to match. See `references/real-worker-canary-admissibility.md` for the full checklist, reversible profile-confinement procedure, reviewer-ID ordering, Windows lock recovery, honest Kanban-versus-cron receipt typing, and recovery handoff.

- A worker can leave useful uncommitted files in an isolated worktree while the card is blocked; review the files, not just the card title.
- **Passes are not acceptance when temporal evidence is involved.** Independently test the aggregate with every timestamped source (receipt, task ledger, provider ledger, activity) later than the injected observation clock. Future evidence must be explicit `MALFORMED`/unsafe (or a documented equivalent) and must never make a planning-safety flag true. Test the aggregate, not only a helper.
- **Do not weaken a red assertion merely to make the handoff green.** When an independent review exposes a fail-open counterexample, preserve or add that regression, reproduce it in an isolated temporary root, then `unblock --reason` with the exact malformed state and required safe result before re-dispatching. Re-review the actual test diff to ensure requested cases were added rather than silently relaxed.
- **Bound the final receipt before decoding it.** Field-level truncation is too late when a syntactically valid receipt contains megabytes of untrusted evidence: cap raw file bytes before `read_text` / `json.loads`, return an explicit unavailable or malformed observation when oversized, and add a regression using a structurally valid oversized receipt. Keep the bound in the pure reader as well as any UI formatter so neither parsing nor rendering can consume unbounded payloads.
- **Chain an explicitly authorized next roadmap slice as an exact dependent card.** Create the next bounded card with `--parent <current-card>` and complete acceptance/exclusions/retention bounds in its body; do not let it start before the parent is canonical and terminal. A scoped supervisor must no-op while the parent is nonterminal. When the released child is `todo`, promote that exact child only. Do not use a board-wide `dispatch --max 1` merely to start it: that command can select unrelated ready work. Let normal gateway dispatch claim the child, then supervise and integrate only that card.
- Generated evidence may prove a fixture path without proving a real provider path. Preserve that distinction in the card result and next-goal scope.
- Worker claims can mention broader-suite failures from missing fixtures or tooling; separate those from failures in the changed files and report both honestly.
- If a card is blocked for review, do not widen it by opening a real canary as a side effect. Integrate the safe bounded change first and create a separately authorized provider goal later.
- **Auto-decomposition after a blocked run can duplicate already-integrated scope.** Before launching the next roadmap slice, inspect the parent and every generated child. If canonical code already satisfies a child, complete that child individually through the CLI with the exact commit, canonical tests, and denied-authority receipt; do not dispatch redundant workers or write the board database directly. A generated card in `todo` cannot be completed directly: use `promote <task_id>` to move it to `ready` first. If a duplicate card is actively running in the already-integrated worktree, use `reclaim <task_id>` to terminate/release that redundant claim and return it to `ready`, then complete it. **The final dependent can be automatically claimed/spawned immediately when its last prerequisite completes.** After every dependency-closing `complete`, immediately inspect the next child; if it is `running`, issue `reclaim` before any further action, then read back the `reclaimed` event and verify host-local termination when applicable before completing it. Traverse the dependency graph from currently-ready prerequisite cards toward dependents; after each completion, `show` the next card and wait for its automatic promotion to `ready`. `complete` accepts `--summary` and `--metadata` only for one task at a time, so loop through duplicate children rather than bulk-closing them. If `complete` reports "unknown id or terminal state", inspect the task graph with `show`: it may be `todo` rather than terminal. Once all generated children are terminal, re-check the original parent: it returns to `ready` and can then be completed with its own structured receipt.
- **Supervisor state machines must distinguish an ordinary dependency wait from post-review auto-decomposition.** A root that changes to `todo` after a blocked review may have a `decomposed` event and generated prerequisite/validation children even though its isolated worktree already contains the reviewed candidate. Do not let a task-scoped supervisor loop forever on the root's `todo` state or blindly dispatch generated workers. Inspect root events and every child; independently validate and integrate the candidate, then close generated children in dependency order with the canonical receipt and complete the restored root. Treat `todo` as an ordinary parent wait only when no post-review decomposition graph exists.
- **Stage discipline with pre-commit hooks:** hooks may stash every unstaged edit before committing. After any post-`git add` source/test edit, stage the intended paths again. After committing, immediately inspect `git show --stat HEAD` and `git status --short`; if a reviewed edit was stashed out, amend the local candidate before promotion, then rerun the relevant acceptance suite.

## Planning-proposal approval boundaries

For autonomous proposal generation that must remain outside runnable Kanban state, follow `references/planning-proposal-ledger.md`. It covers the local append-only observation ledger, provider-free dry-run source, exact hard-false schema validation, read-only VOT/Telegram visibility before authentication, and the later authenticated atomic card-creation handoff. Do not expose unauthenticated `approve`/`review` commands merely as attestations; omit the mutation surface until trustworthy identity exists.

### Operator communication

Keep Brennan's updates minimal by default: **result/status, blocker (only if present), and next step**. Use no more than three short bullets unless he explicitly asks for detail. Do not include tool transcripts, implementation chronology, or long technical explanations. If a complicated issue needs context, give the one-line conclusion first and offer details only on request.

**Explicit quiet-continuation contract:** when Brennan says to proceed autonomously and reply only when finished or when explicit approval is needed, do not send ordinary progress updates, intermediate test counts, or review-start notices. Continue through bounded safe work silently. Surface only a terminal completion, a genuine hard blocker, or a human-gated decision; an environmental or test-lifecycle issue that can be diagnosed and repaired within approved scope is not a reason to interrupt.

Describe the workflow precisely as **agent proposes → human approves → system creates the Kanban card**. The human approves the proposal; they do not manually duplicate it as a card. Distinguish ordinary non-gated agent-created cards from broker/order, risk, scheduler, and promotion work, which remains separately human-gated.
